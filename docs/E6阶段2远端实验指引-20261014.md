## 3. tmux 运行

```bash
tmux new -s e6p2
cd /root/ZX-GBS/ZX-GBS-PO && source .venv/bin/activate
PYTHONPATH=src python scripts/e6_phase2_run.py --shots 1000000 --processes N \
  2>&1 | tee artifacts/e6_paper_replica/phase2/run.log
# Ctrl+B 然后按 D 断开；重连：tmux attach -t e6p2；看日志：tail -f artifacts/e6_paper_replica/phase2/run.log

# 中断后续跑：同一命令重跑即可（fold_results.jsonl 里已完成的折自动跳过）
```

`--processes N` 取值逻辑：N = min(物理核数, 8~16 之间)；每进程单行缓冲 <200MB，
N 进程的内存主要是共享列存储（1M 档 1.02GB，mmap 页缓存共享）+ 主进程计数矩阵
（全行档约 4.2GB/折）。**内存 ≥ 16GB 时 N=8 稳妥；32GB 可到 16**。
`--folds` 支持分批（如先 `--folds 0-9` 再 `--folds 10-19`），断点续跑自动衔接。

## 4. 预计耗时与内存

本地基准（M 系 MacBook）：列打包 1M 档单行 A+B ≈ 13.3ms。换算：**每核每秒约 75 行**直方图。
全量 = 每折约 26 万行 × 20 折 ≈ 520 万行（含 train/valid/test 全部行）：

- 8 进程：520 万 / (75×8) ≈ 8700s ≈ **2.4h** + 每折固定开销（encoder/基选择/评估 ~2min×20）
  + 一次性转置 62s → **合计约 3h**；
- 16 进程（32GB 内存机器）≈ 1.6h。

内存峰值预算：列存储 1GB（共享）+ 计数矩阵 4.2GB/折（主进程）+ worker 缓冲 ≈ **7GB**。
5M 档（列存储 5.1GB + 单行 ×5）约 4 倍耗时，需 ≥12GB 空闲。

## 6. 故障排查

| 症状 | 原因与处理 |
|---|---|
| `FileNotFoundError: sample_store/hardware/hw-5M-b0/packed.npy` | 真机数据未同步或目录层级不对（须在项目根下保持 sample_store/hardware/hw-5M-b0/ 结构） |
| 内存不足/被杀 | 降 `--processes`（worker 缓冲按进程数倍增）；确认无其他大进程 |
| 跑得比预期慢 5×+ | 检查是否用了 `--processes 1`；确认列存储缓存已生成（首次转置 62s 属正常） |
| `numpy` 版本 < 2.0 报 `bitwise_count` 缺失 | 本项目 pattern 引擎主体不依赖 bitwise_count（仅阶段 1 脚本用）；装 numpy≥2 即可 |
| 中断后想清零重跑某折 | 编辑 `fold_results.jsonl` 删除该折行后重跑（或删整个文件全量重跑） |
| 汇总为空 | `fold_results.jsonl` 至少一折才生成 summary.json；先确认折完成 |
| git clone 要求认证 | 仓库为 private 时用 `https://<TOKEN>@github.com/894651749/ZX-GBS-PO.git` 或在服务器配 SSH key |
